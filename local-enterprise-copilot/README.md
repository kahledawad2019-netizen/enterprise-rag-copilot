# Local Enterprise Intelligence Copilot

A production-shaped RAG and analytics system that answers questions about a
company's **policy documents** and its **SQL Server data** — and knows which
one a question needs. Everything runs locally: no cloud LLM, no data leaving
the machine.

```
276 tests passing · 43 data validations · 96 held-out eval questions · NDCG@8 0.946
```

---

## The problem

An enterprise assistant that only reads documents cannot tell you which
customers breached their SLA. One that only queries the database cannot tell
you what the SLA promised. Most real questions need both:

> *"Show customers with more than three SLA breaches and summarise the SLA policy."*

And a system that answers such questions has to get several things right that
demos usually skip: it must not invent citations, must not be talked into
running a `DELETE`, must not show one tenant another tenant's revenue, and must
know that the 2023 refund policy was superseded in 2025.

## What this does

```
question
  |
  +- router          rules first, then a model
  |                  destructive intent -> refused before any SQL is generated
  |
  +- documents       dense + BM25 -> RRF fusion -> cross-encoder rerank -> MMR
  |                  tenant / access-group / version filters applied DURING search
  |
  +- database        relevant schema subset + business glossary + approved examples
  |                  -> T-SQL -> sqlglot guard -> read-only execution -> audit
  |
  +- evidence        [D1..] policy documents   [S1..] database results, kept distinct
  |
  +- answer          local llama3.1, every citation validated against the evidence
```

**Simulated company:** *Northwind Cloud*, a fictional B2B SaaS vendor —
19 policy documents (7,160 words) and ~287,000 database rows across 25 tables.

## Quick start

```powershell
# 1. environment
py -3.13 -m venv .venv
.venv\Scripts\python -m pip install -e ".[dev,rerank,vanna]"
Copy-Item .env.example .env

# 2. local models (~5.5 GB)
ollama pull llama3.1:8b
ollama pull qwen3-embedding:0.6b

# 3. check everything before building anything
.venv\Scripts\python scripts\check_environment.py

# 4. database: schema, then reproducible synthetic data, then assertions
.venv\Scripts\python scripts\setup_database.py
.venv\Scripts\python scripts\generate_synthetic_data.py
.venv\Scripts\python scripts\validate_data.py

# 5. document index
.venv\Scripts\python scripts\build_index.py --rebuild

# 6. ask something
.venv\Scripts\python scripts\copilot.py "what is the refund policy for enterprise annual plans?"

# 7. or use the UI
.venv\Scripts\streamlit run app\streamlit_app.py
```

Full setup, including SQL Server installation: **[docs/setup_windows.md](docs/setup_windows.md)**

## Example questions

| Question | Route | What it exercises |
|---|---|---|
| What is the refund policy for enterprise annual plans? | documents | version filtering — the 2023 policy said *non-refundable* |
| Which five customers have the highest ARR? | SQL | curated views, business glossary |
| Show customers with >3 SLA breaches and summarise the SLA policy | **both** | policy and data cited separately |
| What happened in INC-2025-0042? | documents | exact identifier — dense retrieval returns the *wrong* incident |
| Calculate MRR using the official business definition | SQL | glossary: trials excluded, annual normalised |
| Delete all customers from the database | **refused** | rule-based refusal before any SQL |
| What is the response time? | **clarify** | ambiguous: which tier, which priority? |
| What is the maximum discount? *(as `guest`)* | **no answer** | permission filtering |

## Measured quality

Numbers come from `scripts/evaluate_retrieval.py`. Nothing here is estimated.

### Held-out set — 96 questions the author did not write

Generated by llama3.1 from uniformly sampled passages, with mechanical ground
truth and rule-based filtering only. **Never tuned against.**

| strategy | hit@8 | MRR | recall | **NDCG@8** | mean ms |
|---|---|---|---|---|---|
| dense | 0.990 | 0.811 | 0.990 | 0.856 | 105 |
| sparse | 0.990 | 0.839 | 0.990 | 0.877 | **4** |
| hybrid | 0.979 | 0.906 | 0.979 | 0.925 | 54 |
| **reranked** | **1.000** | **0.928** | **1.000** | **0.946** | 1084 |

### The result that matters most

NDCG split by how much of the question's vocabulary appears in the source
passage — low overlap means least leakage, and hardest:

| overlap | n | dense | sparse | hybrid | reranked |
|---|---|---|---|---|---|
| **low** (hardest) | 33 | 0.721 | 0.778 | 0.845 | **0.870** |
| medium | 45 | 0.927 | 0.918 | 0.981 | 0.981 |
| high (leakiest) | 18 | 0.927 | 0.959 | 0.931 | **1.000** |

Hybrid beats dense by **+17.2 %** on the hardest cases and only **+0.4 %** on
the easiest. An evaluation artifact would show the opposite pattern. Sparse
swings **+23 %** from low to high overlap, which is lexical leakage flattering
BM25 — and why the breakdown is reported rather than the mean.

Bias analysis and remaining limitations: **[docs/evaluation.md](docs/evaluation.md)**

## Features

**Retrieval** — structure-aware chunking that keeps policy clauses and table
headers intact · dense + BM25 hybrid with RRF · local cross-encoder reranking ·
MMR diversity · parent-child expansion · incremental indexing with stale-chunk
deletion · index manifests that refuse a mismatched embedding model.

**Text-to-SQL** — `TextToSQLProvider` interface with **two** implementations
(Vanna and native) sharing one guard and one runner · per-question schema
subset instead of the whole schema · business glossary injected into the prompt
· human-verified few-shot examples.

**Security** — sqlglot AST validation (not regex) · single-statement only ·
schema allow-list · blocked columns · tenant predicate enforced on the parse
tree · row caps · query timeouts · audit written *before* execution · rule-based
refusal of destructive intent.

**Observability** — trace id per request · spans per stage · credentials
stripped and PII masked before anything is written · structured JSON logs ·
optional OpenTelemetry/Phoenix that degrades silently when absent.

## Known limitations

Stated plainly, because a system that hides these is harder to trust.

1. **The read-only database principal is not yet in force.** The instance is in
   Windows-Authentication-only mode, so `copilot_reader` cannot be created
   without enabling Mixed Mode — a server-level change this project will not
   make silently. Until then **only the application guard protects the data**,
   and `check_environment.py` says so on every run. See
   [ADR-003](docs/architecture_decisions/ADR-003-sql-server-readonly-principal.md).
2. **Reranking buys an effect this evaluation cannot resolve** (+2.3 % NDCG,
   p = 0.23). It is now applied adaptively — skipped when dense and sparse
   independently agree on the top result, or when the query names an
   identifier already matched — which skips **52 %** of queries and halves
   median latency (2,428 → 1,454 ms) at a measured cost of 0.0014 NDCG. Set
   `RERANK_POLICY=always` to restore it, or `never` to reclaim the rest.
3. **The held-out set contains only answerable questions.** It says nothing
   about abstention or permissions; the dev set covers those.
4. **The author wrote the documents.** Only the eval questions are independent.
5. **Embedded Qdrant is single-process** — ingestion and the app cannot run
   together. `QDRANT_MODE=server` removes this.
6. **Query rewriting, multi-query retrieval and decomposition are not
   implemented** — deferred deliberately until evaluation shows they help.
7. **SQL Server Express** caps the database at 10 GB.

## Future improvements

Relevance thresholding so abstention is structural rather than heuristic ·
schema-linking evaluation as a separate metric · a genuinely third-party eval
set · Qdrant in server mode with payload indexes · streaming answers.

## CV description

> **Local Enterprise Intelligence Copilot** — Built a production-shaped RAG and
> analytics system answering natural-language questions over 19 policy
> documents and a 287k-row SQL Server database using only local models
> (llama3.1 via Ollama), with no cloud dependency at runtime. Implemented hybrid
> retrieval (dense + BM25 with reciprocal rank fusion and a local cross-encoder
> reranker), achieving **NDCG@8 0.946, +10.5 % over a dense-only baseline**,
> measured on a **held-out evaluation set generated independently of the author**
> and reported with a leakage-band analysis. Built a Text-to-SQL layer behind an
> application-owned provider interface with two interchangeable implementations
> (Vanna and a native provider), where generated SQL is validated by a
> **sqlglot AST guard** enforcing read-only access, schema allow-lists, column
> blocking and tenant isolation — blocking 14/14 attack shapes including
> comment-hidden statement batching and cross-tenant reads. Added a query router
> that refuses destructive intent by deterministic rule before any SQL is
> generated, citation validation that detects fabricated sources, and full
> request tracing with credential redaction. **276 automated tests**, four
> architecture decision records, and documented limitations.

**Stack:** Python · Ollama · SQL Server · Qdrant · BM25 · sqlglot · pydantic ·
Streamlit · OpenTelemetry · pytest
