# Interview guide

## The 60-second version

> I built a local RAG and analytics copilot over a simulated B2B SaaS company:
> 19 policy documents and a 287,000-row SQL Server database. It routes each
> question to documents, to SQL, or to both, and every factual claim is cited
> and validated. It runs entirely on local models through Ollama.
>
> The parts I would point at: hybrid retrieval measured at **NDCG@8 0.946,
> +10.5 % over dense**, on a held-out set generated independently of me; a
> **sqlglot AST guard** that blocks 14 of 14 attack shapes including
> comment-hidden statement batching; and a router that refuses destructive
> requests by rule *before* any SQL is generated — which I added after
> discovering the system would otherwise answer "delete all customers" with an
> unrelated `SELECT`.

## STAR

**Situation.** Enterprise questions span two incompatible sources. A
document-only assistant cannot say which customers breached their SLA; a
SQL-only one cannot say what the SLA promised. Real questions need both, and a
system answering them must not invent citations, run writes, or leak across
tenants.

**Task.** Build a production-shaped system — locally hosted, measurable,
secure — rather than a demo.

**Action.**
- Hybrid retrieval: dense + BM25 fused with RRF, then a cross-encoder reranker,
  MMR for diversity, and parent expansion
- A held-out evaluation set generated by a model from uniformly sampled
  passages, so the numbers are not self-graded
- Text-to-SQL behind an application-owned interface with two interchangeable
  providers, sharing one guard and one runner
- A sqlglot AST guard rather than regex, enforcing read-only, schema
  allow-lists, column blocking and tenant isolation
- A router that refuses destructive intent deterministically
- Citation validation that detects fabricated sources
- Tracing with credential redaction

**Result.** NDCG@8 0.946 (+10.5 % over dense) on held-out questions; 0
permission or version leaks across 42 adversarial cases; 14/14 SQL attacks
blocked; 0 injection payloads obeyed with payloads placed in the evidence; 276
automated tests. Four ADRs, and the limitations documented rather than hidden.

## Questions you should expect

**"Why hybrid rather than just embeddings?"**
> They fail in opposite directions. Dense cannot distinguish `INC-2025-0042`
> from `INC-2025-0031` — I measured it returning the wrong incident at rank 1.
> BM25 gets it right in 1 ms but scores 0.333 on multilingual queries. Fused,
> NDCG went 0.856 → 0.925, and the gain concentrates where it should: +17 % at
> low lexical overlap, +0.4 % at high.

**"How do you know you did not overfit the evaluation?"**
> The 42-case set I wrote is a dev set and I call it that. The numbers I quote
> come from 96 questions a model generated from uniformly sampled passages with
> mechanical ground truth, never tuned against. I also report NDCG by lexical
> overlap band, because model-written questions leak vocabulary and that
> inflates BM25 specifically.

**"How do you stop it running a DELETE?"**
> Three layers. The router refuses destructive intent by rule before SQL exists.
> The guard parses with sqlglot and inspects the tree, so a comment cannot hide
> a second statement. And the DB principal should be read-only — which on this
> machine it is not yet, because the instance is Windows-auth-only. I documented
> that rather than claiming a protection I do not have.

**"Why parse SQL instead of pattern matching?"**
> `SELECT 1 /* hide */ ; DROP TABLE x` defeats a blocklist, as does
> `EXECUTE (...)`. Parsing gives you statement count and node types directly.
> The subtlest case I test is `tenant_id = 1` inside a string literal — a regex
> accepts it as a tenant predicate, the AST does not.

**"What went wrong during the build?"**
> Several things, and they are the most useful part. Incremental indexing never
> worked — I compared the chunk's hash against the document's, so nothing was
> ever skipped. The citation extractor rejected `[D1, 3.1]`, the form the model
> actually produces, so correctly-cited answers were reported as ungrounded.
> And multi-source sent the *document* subquestion to the SQL generator because
> I had assumed the model would order subquestions consistently. Tests caught
> all three.

**"What is the weakest part?"**
> The abstention heuristic. Retrieval always returns top-k, so the evidence
> package is never empty and "the model declined" is inferred from phrasing. The
> right fix is a relevance threshold, which I did not add because the threshold
> would have to be chosen against the held-out set.

**"What would you change at scale?"**
> Qdrant in server mode — payload indexes do nothing embedded, so filters scan.
> A real permission system rather than a user-switching demo. And a larger
> corpus: the held-out set's 96 questions come from only 32 distinct passages,
> so its effective sample size is 32 and effects below +0.05 NDCG are invisible.

**"Tell me about something you measured that turned out wrong."**
> I made reranking conditional to save latency, skipping it when the top fused
> result led the runner-up by 35 %. The rule fired on 2 of 25 queries and the
> evaluation came back byte-identical to before — same NDCG, same wins, losses
> and ties. The threshold was unreachable: RRF scores documents at 1/(k+rank),
> so with k=60 ranks 1 and 2 differ by about 1.6 %, and the largest margin in
> the whole set was 0.112. I had tuned against a number the algorithm cannot
> produce, and my unit tests passed because I wrote them with invented scores
> like 0.9 and 0.4. The fix was to read what RRF actually preserves — rank
> position — and skip when dense and sparse independently rank the same chunk
> first. That fires on half the queries and cut median latency from 2,428 ms to
> 1,454 ms for 0.0014 NDCG.

**"Why not LangChain or LlamaIndex?"**
> Every stage had to be independently testable and measurable. I need to be able
> to say "fusion contributed +8 %" and "reranking hurt exact_code by 15 %". A
> framework owning routing and tool selection makes those questions much harder
> to answer, and the retrieval and safety logic is where the substance is.

## Demo script (5 minutes)

1. **Policy question** → citation with version and effective date
2. **`INC-2025-0042` in the Retrieval Debugger** → dense returns the *wrong*
   incident; sparse fixes it
3. **Data question** → generated SQL shown, guard verdict, rows, answer
4. **Multi-source** → `[D...]` policy and `[S...]` data cited separately
5. **"Delete all customers"** → refused by rule, no SQL generated
6. **Switch to `guest`, ask about discounts** → permission filtering
7. **SQL Analytics page** → paste a comment-hidden `DROP`, watch it blocked
8. **Evaluation page** → the leakage-band table, and why it is the honest number
