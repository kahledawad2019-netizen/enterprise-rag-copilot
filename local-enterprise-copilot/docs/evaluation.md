# Evaluation

Two evaluation sets, used for different purposes. Conflating them is how RAG
projects end up quoting numbers that do not survive contact with real questions.

| Set | Cases | Written by | Purpose |
|---|---|---|---|
| `evals/document_rag.jsonl` | 42 | the author | **dev set** — regression guard, adversarial coverage |
| `evals/document_rag_holdout.jsonl` | 96 | llama3.1:8b | **test set** — generalisation, never tuned against |

---

## 1. Why a held-out set was necessary

The 42-case dev set was written by the same person who wrote the documents and
the chunker, with knowledge of how retrieval was implemented. That makes it
useful for catching regressions and worthless as evidence of generalisation.
Reporting its numbers as a benchmark would be measuring how well the system
matches its author's expectations.

## 2. How the held-out set removes author bias

`scripts/generate_eval_set.py`:

1. **Uniform sampling.** Two chunks are sampled per document across the whole
   corpus with a fixed seed. The author does not choose which passages are
   tested, so passages that retrieval handles badly cannot be quietly avoided.
2. **Questions written by the model, not the author.** llama3.1:8b reads a
   passage and writes questions from it. The author never sees the passage
   before the question exists.
3. **Mechanical ground truth.** The relevant document is the one the chunk came
   from. No human judges relevance after seeing results.
4. **Rule-based filtering only.** Generated questions are rejected by fixed
   rules (too short, not a question, mentions "this document"). Hand-picking
   the survivors would reintroduce the bias being removed.

## 3. The bias that remains — stated, and measured

**Lexical leakage.** A model writing a question from a passage tends to reuse
its vocabulary, which inflates BM25 specifically. This is not eliminated, so it
is quantified: every case records the share of its question's words that appear
in the source passage, and results are reported by band.

| Band | Cases | Meaning |
|---|---|---|
| low (<0.35) | 33 | least leakage — hardest, most realistic |
| medium | 45 | |
| high (>=0.6) | 18 | most leakage — flatters BM25 |

Mean overlap across the set: **0.431**.

**Other limitations, stated plainly:**

- The author still wrote the documents, so the domain and writing style are the
  author's. Only the questions are independent.
- Ground truth is the source document. A question may be legitimately
  answerable from a second document; that counts as a miss, so these numbers
  are a **lower bound**, not an optimistic one.
- The held-out set contains **only answerable questions**. It says nothing
  about abstention, permissions or injection resistance — the dev set covers
  those, and the two are complementary rather than interchangeable.
- 96 cases is small. Differences under roughly 2 points should not be treated
  as meaningful.
- Questions were generated by llama3.1:8b, the same model used for answer
  generation later (though not for embedding or reranking).

## 4. Results

### Held-out set (96 cases, k=8) — never tuned against

| strategy | hit@k | MRR | recall | precision | **NDCG** | mean ms |
|---|---|---|---|---|---|---|
| dense | 0.990 | 0.811 | 0.990 | 0.241 | 0.856 | 105 |
| sparse | 0.990 | 0.839 | 0.990 | 0.218 | 0.877 | **4** |
| hybrid | 0.979 | 0.906 | 0.979 | 0.233 | 0.925 | 54 |
| **reranked** | **1.000** | **0.928** | **1.000** | 0.177 | **0.946** | 1084 |

### Dev set (42 cases, k=8) — used during development

| strategy | **NDCG** |
|---|---|
| dense | 0.800 |
| sparse | 0.797 |
| hybrid | 0.871 |
| reranked | 0.886 |

### The two sets are not directly comparable

Held-out scores are **higher** in absolute terms, and that is expected rather
than suspicious: the dev set deliberately includes unanswerable, ambiguous,
permission-denied and prompt-injection cases that drag the mean down, while
every held-out case is answerable by construction.

**What matters is that the ordering and the size of the gaps hold:**

| improvement over dense | dev set | held-out |
|---|---|---|
| sparse | -0.4 % | +2.5 % |
| hybrid | **+8.8 %** | **+8.0 %** |
| reranked | **+10.7 %** | **+10.7 %** |

The hybrid and reranking gains reproduce almost exactly on questions the author
never wrote. That is the result this section exists to establish.

## 5. The most informative result: performance by leakage band

| overlap | n | dense | sparse | hybrid | reranked |
|---|---|---|---|---|---|
| **low** (hardest) | 33 | 0.721 | 0.778 | 0.845 | **0.874** |
| medium | 45 | 0.927 | 0.918 | 0.981 | 0.981 |
| high (most leakage) | 18 | 0.927 | 0.959 | 0.931 | **1.000** |

Three things follow, and the first two are the important ones.

**1. Hybrid's advantage is largest exactly where the questions are hardest.**
At low overlap, hybrid beats dense by **+17.2 %**; at high overlap, by only
+0.4 %. If hybrid retrieval were an artifact of the evaluation design, the gain
would concentrate in the easy, high-leakage cases. It does the opposite.

**2. Leakage does flatter BM25, as predicted.** Sparse rises from 0.778 at low
overlap to 0.959 at high overlap, a **+23 %** swing driven by vocabulary
overlap rather than retrieval skill. Anyone quoting a single sparse number
without this breakdown is over-reporting.

**3. Reranking's benefit also concentrates in the hard cases** (+21 % over
dense at low overlap). This is consistent with what a cross-encoder does: it
reads query and document together, which matters most when they do not share
vocabulary.

## 6. What the dev set still covers that the held-out set cannot

| Property | Result (dev set) |
|---|---|
| Filter correctness — no permission or version leak | **1.000** all strategies |
| Abstention on unanswerable questions | **7/7** |
| Guest reaching the finance-only pricing policy | never |
| Superseded policy surfacing as current | never |
| Injection-test document in default retrieval | never |

These are adversarial properties. They cannot be generated by asking a model to
write questions from a passage, because the correct behaviour is to return
*nothing*.

## 7. Reproducing this

```powershell
# regenerate the held-out set (deterministic given COPILOT_SEED)
.venv\Scripts\python scripts\generate_eval_set.py

# held-out — the number to quote
.venv\Scripts\python scripts\evaluate_retrieval.py --holdout --k 8

# dev set — regression guard
.venv\Scripts\python scripts\evaluate_retrieval.py --k 8 --compare-baseline
```

`--compare-baseline` exits non-zero if any strategy regresses by more than
0.02 NDCG against `evals/baseline_retrieval.json`.

## 8. Rules this project follows

- **Never tune against the held-out set.** If it is used to choose a chunk
  size, a `k`, or a reranker, it stops being held out and a new one must be
  generated.
- **Quote held-out numbers** for quality claims; quote dev-set numbers for
  regression and adversarial behaviour.
- **Report the leakage band breakdown**, not just the mean.
- **State the remaining bias** every time the numbers are used.
