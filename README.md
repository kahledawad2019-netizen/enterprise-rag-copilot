# Northwind Enterprise Copilot

A retrieval-augmented assistant over company policy documents: hybrid search
(dense + BM25), permission-aware retrieval, citation-validated answers, and a
chat UI with streaming, source previews and document upload. It runs in two modes
from one codebase:

| | Local / private | Cloud / public |
|---|---|---|
| Chat model | Ollama (auto-picks an installed model) | Groq (`llama-3.3-70b-versatile`) |
| Embeddings | Ollama `nomic-embed-text` | fastembed ONNX (same nomic family), in-process |
| Hosting | your machine | Render free plan, one Docker container |
| Leaves the machine | nothing | question + retrieved passages go to Groq |

## Run it locally

```powershell
ollama serve            # if Ollama is not already running
.un_local.ps1         # Windows  (./run_local.sh on macOS/Linux)
```

Then open http://127.0.0.1:8000.

## Deploy it

Render -> New -> Blueprint -> this repository -> paste a Groq key. Details,

## How it works

[docs/RAG_ARCHITECTURE.md](docs/RAG_ARCHITECTURE.md) traces a question from
ingestion to cited answer, with measured retrieval quality and known
weaknesses. The application code is in `local-enterprise-copilot/`, the API
and UI in `cloud/`.

# Legacy prototype (repository root scripts)


Ask your SQL Server database questions in plain English. Retrieval runs against
a local ChromaDB store, SQL is generated by **llama3.1 running in Ollama on this
machine**, and the query executes against SQL Server through a read-only
guardrail.

Nothing — not your schema, not your questions, not your data — is sent to a
hosted LLM.

```
question ──> ChromaDB retrieval ──> llama3.1 (Ollama) ──> T-SQL
                  (DDL, docs,                                │
                   example SQL)                              ▼
                                                   read-only guardrail
                                                             │
                                                             ▼
                                                   SQL Server ──> DataFrame
```

## Configuration

All settings live in `.env` and are loaded and validated by `src/settings.py`.
Precedence: **real environment variables → Windows Credential Manager → `.env`**.

Switching databases is a one-line change:

```ini
MSSQL_DATABASE=Company_SD
```

Then re-run `python -m src.train` — the corpus is per-database, so retrain when
you switch. Other databases on this instance: `TRAINING`, `ITI`, `Company_SD`,
`BikeStores`, `Test`, `ud_cms`.

## Security

Seven measures are already in place.

**1. Secrets never reach git.** `.gitignore` excludes `.env` (and `*.key`,
`*.pem`, `secrets/`). `.env.example` is the only committed config file.
`check_env.py` fails if that ever stops being true.

**2. The password is never printed.** It is a pydantic `SecretStr`, so logging
or dumping the settings object shows `**********`. The only place it is
unwrapped is `odbc_connection_string()`; use `safe_connection_string()` whenever
you need to display it.

**3. Windows Auth by default.** The current setup uses
`Trusted_Connection=yes` — there is no password stored anywhere on disk. If you
must use a SQL login, run `python scripts\set_secret.py` to put the password in
the Windows Credential Manager (DPAPI-encrypted under your account) instead of
leaving it in `.env`.

**4. The connection is encrypted.** `Encrypt=yes` always.
`TrustServerCertificate=yes` is set because the local instance uses a
self-signed certificate — **set it to `false` before pointing this at any
remote server**, otherwise the connection is vulnerable to interception.

**5. Generated SQL is treated as untrusted.** `src/security.py` rejects
anything that is not a single read: non-SELECT statements, batched statements
(`;`), `SELECT ... INTO`, `EXEC`/`sp_`/`xp_`, `OPENROWSET`, `BACKUP`, and more.
Comments and string literals are stripped before the check so
`SELECT 1 /* hide */; DROP TABLE t` cannot slip through. Results are capped at
`MAX_ROWS`. Verified against 8 unit cases and 6 live attack attempts.

**6. The UI is loopback-only.** `.streamlit/config.toml` binds to `localhost`
(Streamlit otherwise listens on `0.0.0.0`, exposing your database to the LAN),
disables telemetry, and hides tracebacks that could leak schema details.

**7. Your data stays local.** Ollama and ChromaDB both run on this machine, and
ChromaDB telemetry is disabled. `ALLOW_LLM_TO_SEE_DATA=false` additionally stops
Vanna from feeding query *results* back into the prompt.

### One thing still to do: a least-privilege login

`check_env.py` currently warns:

```
[WARN]   privileges  -  this login can WRITE.
```

You are connecting as a Windows admin, so the guardrail in `security.py` is the
only thing standing between an LLM mistake and your data. A guardrail in the
application is not a security boundary — the database should refuse writes by
itself.

Run `sql/create_readonly_login.sql` (edit the password and database name first),
then switch `.env` to that login. The warning turns into
`[ OK ] privileges - read-only login`, and you have defence in depth.

## Improving answer quality

Retrieval quality is what makes or breaks this system. In order of impact:

1. **Question/SQL pairs** — by far the strongest signal. Add them to
   `training/question_sql_pairs.json`, or click *Save as a correct example* in
   the UI after a good answer.
2. **Business documentation** — edit
   `training/documentation/00-business-glossary.md`. The schema cannot tell the
   model what "active customer" means, which table is authoritative, or that a
   column called `status` holds `1 = shipped`.
3. **DDL and foreign keys** — extracted automatically by `python -m src.train`.

Raise `N_RESULTS` in `.env` to retrieve more context per question; raise
`OLLAMA_NUM_CTX` if the prompt starts getting truncated on a wide schema.

## Notes on this build

Two upstream issues are worked around in `src/vanna_agent.py`, both documented
inline:

- **`extract_sql` truncated bracketed identifiers.** Vanna's Ollama adapter cuts
  its response at the first `[`, so `SELECT [State], COUNT(*) ...` became
  `SELECT `, which then failed at the server. Bracket-quoted identifiers are
  ordinary T-SQL, so `extract_sql` is overridden with a version that handles
  them, fenced code blocks, and CTEs.
- **Vanna prints full prompts to stdout.** `log()` is routed into the standard
  logger. Set `VERBOSE=true` in `.env` to get the raw prompts back for
  debugging.

`vanna` 2.x is an agent framework with a different API; this project uses the
stable classic interface at `vanna.legacy.*`, which ships in the same package.
